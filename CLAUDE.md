# CLAUDE.md — wow-addon plugin

## Purpose & stack

A **Claude Code plugin** (not a WoW addon itself) that ships helpers for World of Warcraft addon development: standard-compliant scaffolding, compliance auditing, standards-reference revendoring and cross-repo learning harvesting (the two halves of the standards cycle), LibKa0s re-vendoring and new-surface adoption (the consumer-side half of the *library* cycle — a different cycle, sharing only the word "revendor"), interface/version bumping, doc sync, test-battery running, automated-test recording, in-game perf-run recording and analysis, changeset finalization, the six-command `issue-*` family (discovery, triage, listing, detail, summary, hand-filing) over a GitHub-issue store keyed on `state:` and `severity:` labels, execution-status reporting (progress, percent complete and time to finish for a conversation's planned work), git diff/commit, a line-ending hook, and a WoW-specific review subagent. Everything here is **Markdown command/agent specs + hook scripts (the line-ending hook, and the bounded-runs hook with its Python matcher and `ka0s-bounded` runner) + JSON manifests** — there is no compiled code; the one test suite is `scripts/test_bounded_runs.py`, for the matcher.

Current version: **2.3.0** (in `.claude-plugin/plugin.json`). The minor bump is the bounded-runs hook and its `ka0s-bounded` runner: additive, and no caller breaks. The 2.2.0 minor before it was `execution-status`, also additive. The 2.1.0 minor before that was `revendor-libka0s`, also additive. The 2.0.0 major bump before it was the issue store moving from a `[status]` **title prefix** to `state:` + `severity:` **labels**, and the `issue-*` command-name standardization that came with it (`add-issue` → `issue-add`, `fetch-issues` → `issue-fetch-all`) — both break callers.

**This repo ships nothing to the WoW client, so it pins LF** (Ka0s WoW Addon Standard,
`line-endings-§2`). Its root `.gitattributes` carries the non-client canonical body — `* text=auto
eol=lf`, `*.sh text eol=lf`, binaries marked `binary`. Write LF here. The `*.sh` carve-out is not
decorative in this repo: `scripts/normalize-eol.sh` is the hook Claude Code executes, and a shebang
followed by CRLF makes the kernel look for an interpreter literally named `bash\r`.

## Module/package map

- `.claude-plugin/plugin.json` — plugin manifest; **the single source of truth for the version**.
- `.claude-plugin/marketplace.json` — marketplace entry; carries a **mirror of the description** (no version field of its own).
- `commands/*.md` — 22 slash-command specs (`/wow-addon:<name>`), each also invocable as a Skill of the same name. Two of them (`review.md`, `standards-audit.md`) are thin **wrappers that dispatch to the subagent of the same name**; the other twenty act directly.
- `agents/*.md` — 2 subagent specs: `review` (WoW-specific principal-level review → `docs/reviews/<date>/`; also fetches the standard to keep its own remediation compliant, but does **not** audit) and `standards-audit` (read-only compliance audit → `docs/audits/<date>/`, over a three-kind rotation rather than addons alone).
- `hooks/hooks.json` + `scripts/normalize-eol.sh` — the line-ending-normalization hook. It normalizes a just-written file to whatever `.gitattributes` declares for it — **CRLF** or **LF** — and exits silently when nothing is declared (`line-endings-§2`). It reads `text` **and** `eol`, never `eol` alone: `binary` expands to `-text` and says nothing about `eol`, so a marked PNG in a CRLF-pinned repo answers `eol: crlf` for a file git will never convert, and rewriting its bytes on that answer corrupts the asset (`line-endings-§7`). Renamed from `normalize-crlf.sh` when it gained the LF arm; the old name described half of it.
- `hooks/hooks.json` + `scripts/bounded-runs-hook.sh` + `scripts/bounded_runs.py` + `scripts/ka0s-bounded` — the **bounded-runs** `PreToolUse(Bash)` hook and the runner it points at. The hook refreshes the `~/.claude/wow-addon/bin/ka0s-bounded` symlink (the one path specs name, stable across plugin-cache version directories), then denies a heavy run (`lua tests/run.lua`/`tests/perf.lua`, `run-automated-tests.sh`, `luacheck`, `lizard`) that is not prefixed with the runner, not bounded by hand (`ulimit -v` **and** `timeout`), not opted out (`KA0S_BOUNDED_HOOK=off`), and — for Lua runners only — not in a repo whose `tests/_kit` is kit revision **23+** (that kit self-bounds with the same `KA0S_KIT_*` variables). It **fails open**: any error exits 0 silently. The matcher is a tokenizer, not a shell parser — false negatives on exotic shell are acceptable, false positives on ordinary commands (`grep lua tests/run.lua`) are not. Every spec that runs a suite prefixes the runner and says parallel runs are fine because the slot pool bounds them; keep that true when adding one.
- `README.md` — user-facing docs. `LICENSE` — MIT.

## Entry points & lifecycle

Claude Code auto-discovers `commands/` and `agents/` by directory; there is no registration file listing them. A command file becomes live the moment it exists and the plugin is (re)loaded. `hooks/hooks.json` registers the `PostToolUse` hook. To activate changes in a session: **`/reload-plugins`** (no restart needed).

- **Command spec** = YAML frontmatter (`description`, `argument-hint`, `allowed-tools`) + a Markdown body that instructs the agent. `$ARGUMENTS` is the user's argument string.
- **Agent spec** = frontmatter (`name`, `description`, `tools`) + body. The `name` becomes `wow-addon:<name>` when dispatched.

## Configuration & env

No env vars and no config files. **One piece of persistent state**, added with the backgrounded triage writes: `issue-triage` keeps a per-run decision journal under `~/.claude/wow-addon/issue-triage/<scope>-<YYYYMMDD-HHMMSS>.jsonl`. It is outside the session on purpose — a scratchpad journal survives a failed API call but not a crashed session, and the journal exists precisely so a decision the user made can be recovered by a *later* run. A journal missing its `complete` line is an unreconciled run, and that is the only signal the resume check uses. No other spec reads or writes it, nothing prunes it automatically, and no command may treat it as a cache of issue state — GitHub is the store, the journal is the record of what was decided. Some specs need external tools **on the machine of whoever runs them** (still not local plugin config): `standards-audit`, `new-addon`, `revendor-standards`, `automated-tests` and `perf-analysis` fetch the external **[`WowAddonStandards`](https://github.com/tusharsaxena/WowAddonStandards)** repo at runtime (raw GitHub, needs network); `issue-fetch-all`, `issue-add`, `issue-triage`, `issue-summary` and `issue-details` shell out to the **`gh`** CLI (must be installed and authenticated), and `issue-audit` uses it too but treats an absent/unauthenticated `gh` as a skipped sweep rather than a failure; `revendor-libka0s` is the exception on the *library*, and for the same reason: it reads the sibling **`LibKa0s`** checkout off local disk rather than fetching, because its payload is bytes (seventeen `.lua` files as of v1.42.0, an `.xml`, `LICENSE`, and a `media/` subtree of icon TGAs, textures and a font) taken from a **git tag** via `git archive` — no checkout, no run, and no raw-GitHub fallback; it also needs `gh` to file the declines its interview records, and reports an unfiled decline rather than degrading silently. `harvest-standards` is the exception on the *standard* — it runs *inside* the standards repo and reads it from the **working tree** (it is about to edit those files), while reading every sibling addon repo off local disk, so it needs the collection checked out beside it rather than a raw-GitHub fetch, though its closed-issue sweep still goes through `gh` and so still needs network; `run-tests` invokes whatever it finds — **luacheck** and a **Lua** interpreter — treating an absent tool as a skipped suite, not a failure; `standards-audit`, `bump-version` and `review` additionally shell out to **`lizard`** for the complexity report, and all three treat its absence as *not run / report is stale*, never as a failure or a fabricated number — `review` also re-runs `luacheck` and the addon's Lua suites for the same reason, with the same skip-don't-fabricate rule.

## Build / test / run

- **One test file:** `python3 scripts/test_bounded_runs.py` covers the bounded-runs matcher and hook script (run it after touching either). Otherwise **no build, no tests.** Validation is: `python3 -c "import json; ..."` on the two manifests, and a manual `/reload-plugins` to confirm the plugin loads (`Reloaded: … plugins · … skills · … agents · … hooks`).
- The line-ending hook script is Bash; there's no harness for it beyond running the flow that triggers `Write|Edit|MultiEdit` inside a repo that declares an `eol`. **Validate both arms** — the `crlf` arm needs a client-bound repo (any addon, or `LibKa0s`), and the `lf` arm is exercised inside **this** repo, which pins LF. Two more cases matter as much as either, and both must come back byte-identical: a path with no declared `eol`, and a file marked `binary` **inside a CRLF-pinned repo** — the pin answers `eol: crlf` for it, so only the `text` half of the query saves it. Test that one on a **copy** of an addon repo, never a live one, and check with `cmp`.

## Conventions & hot zones (footguns)

- **Adding/removing a command or agent is a 4-touch change.** Keep these in sync or the docs drift:
  1. the `commands/*.md` or `agents/*.md` file,
  2. the README table (Commands / Subagents),
  3. **both** manifest descriptions (`plugin.json` + `marketplace.json`),
  4. the version in `plugin.json` (bump it).
- **Command wrappers for subagents** (`review`, `standards-audit`) are documented under **Subagents** in the README, not the Commands table — follow that taxonomy for any future wrapper.
- **Runtime-fetch specs** (`standards-audit`, `new-addon`, `revendor-standards`, `automated-tests` — which fetches the `AUTOMATED_TESTS.md` playbook alongside the standard's index — `perf-analysis`, which fetches `PERF_ANALYSIS.md` the same way, and, for its guardrail only, `review`): fetch the playbook + standard with `curl -fsSL` (verbatim); WebFetch is a **lossy fallback only** — its summarizer mangles verbatim content. If the standard can't be resolved: `standards-audit`/`new-addon`/`revendor-standards` must **hard-stop** (their whole output is worthless without it), but `review` must **degrade gracefully** — it fetches the standard only to keep its own remediation compliant, so on failure it proceeds with the review and notes that the standards cross-check was skipped. Don't "fix" `review` to hard-stop.
- **Hard-code only the entry points; discover the rest by following links.** The standard is **split** — `standards/STANDARDS.md` is an index whose **Sections** list links one file per section under `standards/standards/`. Specs fetch `STANDARDS.md` and then **every section file it lists**; they **must not** hard-code section filenames, so the standard can be re-organized upstream without touching this plugin. The only fixed remote paths are the playbooks (`AUDIT.md`/`NEW_ADDON.md`/`AUTOMATED_TESTS.md`/`PERF_ANALYSIS.md`), `standards/STANDARDS.md`, and `standards/NEW_ADDON_CONTEXT.md` (fetched verbatim at scaffold time and read from a scratch path — **never** written into an addon repo; a stored `docs/agent-context.md` is anti-pattern #49).
- **A Ka0s addon's root is three docs plus `LICENSE`** — the full `README.md`, the **stub** `CLAUDE.md`, and `DEPENDENCIES.md` (the toolchain contract: every dependency with the evidence for it, split runtime / development / release-and-assets, WSL2-Ubuntu install commands that actually work, one-line verification per tool). **Its `docs/` is the canonical trio** — `ARCHITECTURE.md`, `testing.md`, `smoke-tests.md` — **plus five verification-and-record docs** (the generated `test-cases.md`, `performance.md`, `perf-analysis/README.md`, `automated-tests/README.md`, and the generated `automated-tests/RESULTS.md`) — four of those five are unconditional, and `perf-analysis/README.md` is required **only while the perf harness is wired**, so an addon holding the `performance-§12` no-combat-path exemption ships four of them and no `docs/perf-analysis/` at all — **plus the six unconditional Tier 1 topic-detail docs** (`scope.md`, `module-map.md`, `schema.md`, `settings-panel.md`, `data-flow.md`, `common-tasks.md`), with **Tier 2** (`slash-dispatch.md`, `midnight-quirks.md`, `compat-layer.md`, `message-bus.md`, `profiles.md`, `debug.md`) required per its stated trigger and otherwise recorded as a *Not applicable* row in `ARCHITECTURE.md`'s `## Documentation map`, and **Tier 3** addon-specific and free-form (documentation-§3). **`## Documentation map` has four tables, not three** — Required, Conditional, **Verification and record** and Addon-specific: the seven docs that belong to no tier (`testing.md`, `smoke-tests.md` and the five record docs) had no table until the standard named the fourth, and all nine addons had written it themselves; `perf-analysis/README.md` is the one of the seven that registers in Conditional instead, against its Tier 2 trigger, and whether `ARCHITECTURE.md` registers itself is a **MAY** no spec may file either way. There is **no** `docs/complexity.md` (retired in standard v2.19.0), **no** `docs/file-index.md` or `docs/conventions.md` (retired v2.23.0), and **no** `docs/agent-context.md`; the root `CLAUDE.md` stub is the only agent brief in the repo. **Never state any of these counts without naming its members** — an unfilled slot is what makes a spec reconstruct a deleted file from memory.
- **Automated test records are recorded, and only two of the four suites gate.** The vendored `tests/_kit/run-automated-tests.sh` runs lint, the headless harness, the offline perf scenarios and `lizard`, writing a frozen bundle per run to `docs/automated-tests/<YYYYMMDD-HHMMSS>/` plus a row in `RESULTS.md` — **one** file overwritten in place so git history is the trend line. **`lint` and `tests` gate; `perf` and `complexity` never fail a run** — a threshold that fails a run teaches everyone to reach for `--no-verify`. A missing tool is a **skip recorded with its reason**, never a pass. A full bundle is produced at **release**, before the tag, and never gates a commit. `docs/complexity.md` was retired in standard v2.19.0.
- **Two recording commands, two harnesses, and the line between them is load-bearing.** `/wow-addon:automated-tests` **runs** four out-of-game suites and records what they produced; it owns `docs/automated-tests/`. `/wow-addon:perf-analysis` **cannot run anything** — the measurement happened in a live client on the player's machine, and it reaches this session only as a paste (the printed report plus the one-line JSON dump); it owns `docs/perf-analysis/<YYYYMMDD-HHMMSS>/`. The failure that separation prevents: an agent handed half a paste, or none, filling the gap from the offline `tests/perf.lua` scenarios — an offline `bytes/iter` cited as in-game evidence conflates two harnesses the standard deliberately keeps apart, and the resulting bundle reads as measured when nothing measured it. No report and no dump means **ask and stop**, never a bundle. Neither command may write into the other's tree.
- **A complexity number in Lua is not read the way it is elsewhere, and a disposition expires.** `lizard` counts every `and`/`or` short-circuit as a decision, so a run of `t.k = rec.k or D.k` defaulting lines scores CCN 13 with no visible branching — a high number usually means dense **defaulting/guarding**, not tangled control flow, and the fix is a module-level data table plus one loop rather than restructured logic. Any spec that writes a watch-list disposition must treat **Accepted** as having a shelf life: carried across three consecutive release runs, the entry is owed a fix or a tracked deviation ID (anti-pattern #53). And a refactor triggered by the report is itself constrained (`performance-§11`) — no body dumped into a nameless helper (#52), no dispatch table built inside the function it serves, no behavior change in a mechanical diff, and a characterization test **before** refactoring anything untested.
- **Two checkpoints, two different gates.** **Commits** are gated on lint + the headless harness only (`testing-§4`), and `perf`/`complexity` never fail a run — that rule is retained verbatim, and the vendored runner's exit code **MUST NOT** be changed to implement any threshold, because the same script is the commit gate. **Releases** are gated on all four suites plus **zero functions above CCN 15**, evaluated by `/wow-addon:bump-version` reading the run's `manifest.json` **before it edits anything** (`automated-tests-§3`, *The release gate*). A `skip` is not a pass: an unmeasured suite blocks the release as NOT EVALUATED. The asymmetry is the point — a commit gate is routed around with `--no-verify`; a release has no such hatch.
- **`docs/complexity.md` is retired (standard v2.19.0).** The raw report is each bundle's `complexity.txt`; the trend line and watch list are `docs/automated-tests/RESULTS.md`. No spec may scaffold, regenerate or sync a `docs/complexity.md` — finding one in an addon is a **pre-adoption finding to report**, never a doc to keep current.
- **`review` measures before it reviews, and only what runs outside the game.** Its Step 0 re-runs `luacheck`, the headless suite, a fresh `--list` inventory, `tests/perf.lua`, `lizard`, any `Makefile` `test` target, the vendored-copy `diff`, and the four-class **cross-addon pass** — because a committed artifact is a claim about a *past* state of the code, and the review is about the present one. The cross-addon pass is the one step that reads *outside* the addon under review: the collection's stated deployment is all nine loaded at once, and a collision between two addons that are each correct alone is invisible to every per-addon suite, since each repo tests its own copy and both stay green. Two invariants hold it up and both are easy to break by simplifying it. Every census is scoped to the **TOC-derived load list**, not `grep -r` over the repo — a `RegisterChatCommand` sweep through `libs/` reports a token from a vendored Ace3 comment, and a raw-`SLASH_*` sweep that keeps PrettyChat's tracked-but-unloaded `GlobalStrings/GlobalStrings.lua` reports 359 violations where the loaded source has none. And the clean result is **written down as a baseline table** so the next pass diffs against it instead of re-deriving it; a recorded non-finding is what makes it cheap enough to actually get run. Two boundaries hold it in place: **fresh output goes to scratch, never into the repo** (the inventory moves with the change that moves the pass count; the complexity report moves at release), and **anything needing a login is not run** — it is written up in `03_SMOKE_TESTS.md` for a human. A missing tool is a **stated skip**, never an inferred pass and never a silent fallback to the committed artifact. This is measurement in service of findings, not a gate: `run-tests` still owns running suites as a gate and offering to fix them, and `review` reports a red suite rather than fixing it mid-review.
- **Reference the standard's sections as `filename-§N`.** A whole section is its bare filename (`architecture`, `anti-patterns`); a subsection is `filename-§N` (`architecture-§5`, `documentation-§1`), the number being that section's **local** count. The old global `§N.M` notation is retired — don't use or reintroduce it in specs or artifacts.
- **Artifact directories in the target addon, and the one store that isn't a file.** Three specs write dated bundles into the addon they operate on, and each owns its own tree: `review` → `docs/reviews/<date>/`, `standards-audit` → `docs/audits/<date>/`, `revendor-libka0s` → `docs/revendor/<date>/`. All three are **frozen history** — `issue-audit` reads their execution plans to find unexecuted rows but must never edit them. The pending store is **not a file**: `docs/pending/LEDGER.md` is **retired** and its store is **GitHub issues on the addon's own repo**, so no spec may create, recreate or mirror that ledger. Every issue carries exactly **two labels** that are the data: one `state:` label and one `severity:` label.

  **Status** — `state:done` (green `00ff00`, closed) and `state:will-not-do` (blue `0000ff`, closed) are **terminal**, dropped entirely on later runs; `state:triaged` (yellow `ffff00`, open) is a decided "not now", collapsed to a count; `state:untriaged` (red `ff0000`, open) means nobody has been asked, so it must never read as agreement.

  **Severity** — `severity:critical` (red `110000`), `severity:high` (orange `110800`), `severity:medium` (yellow `111100`), `severity:low` (green `001100`), against the ladder `issue-audit` defines. It is not decoration: it is the **queue order** `issue-triage` interviews in and a reporting dimension in both read commands, so a wrong severity puts an item in front of or behind the wrong things.

  Matching is on the item ID + **evidence hash** in the issue body, so an item only re-opens if its evidence changes. **The labels are the data, and the title carries neither.** Two conventions preceded them and both are retired: the `marker + word` ledger-table affordance (`🟢 done`), and the `[<Status>] <Title>` **title prefix**. Never reintroduce either, never write a severity word into a title, never add a fifth value to either set or rename one, and never keep a second copy of either in the body — the body records the severity *rationale*, not the level. A leftover `[status]` prefix on an old issue is stale text: **the label wins**, and the prefix is stripped by the write commands as part of the stray repair. **Every issue always carries both labels**, so there is no unlabelled state: an issue that arrives without a `state:` label (web UI, or someone not using these commands) is **repaired on sight** to `state:untriaged`, and the repair is **always announced**, including by the two read commands, because a listing command that mutates silently is worse than one that doesn't repair at all. A missing `severity:` label is repaired only by the commands that read bodies (`issue-audit`, `issue-triage`); the read commands show it as `—` and say how many, because a severity guessed from a title alone lands in a grid people then reason from. Any spec that creates the labels does so with `gh label create --force`, which is idempotent and repairs a drifted colour on the way.
- **Discovery and triage are separate commands, and the separation is load-bearing.** `issue-audit` sweeps and files `state:untriaged` with a severity; it **never interviews and never changes code**. `issue-triage` interviews and records; it **changes the issue store only**. Neither writes Lua. A sweep is mechanical and safe to run over every repo at once; a triage costs a human decision per item — fusing them gated the cheap half behind the expensive one. Consequences a spec must respect: triage **records rather than implements**, so accepting an item produces a `state:triaged` issue carrying the approach, not a code change; an early stop leaves the remainder `state:untriaged` and **untouched**, so silence is never a decision and nothing is published that the user never saw; and `gh` is **load-bearing** — without it neither command can run and both must stop rather than degrade. Every decision recorded is **public**, which `issue-triage` must say up front rather than let the user discover from a notification.
- **All issue work goes through the `gh` CLI subcommands** — `gh issue list`, `gh issue create`, `gh issue edit`, `gh issue close`, `gh issue comment`, `gh issue view`, with `--json` where structured data is needed. **Never `gh api graphql`**, and never a hand-rolled GraphQL query against `api.github.com/graphql`: reaching for GraphQL first is a real, observed failure that burns a round trip on a deprecated path before falling back. `gh api repos/{owner}/{repo}/issues` is the only acceptable REST fallback. Because status and severity live in **labels**, listing by either is a plain **`--label` query** over `gh issue list --json number,title,state,labels` — not a title filter, not `--search`, not GraphQL. The label-writing subcommands `gh label list` and `gh label create --force` are in-surface for the specs that ensure the eight collection labels exist. This binds `issue-audit`, `issue-add`, `issue-fetch-all`, `issue-summary`, `issue-details`, `issue-triage`, `harvest-standards` and the `standards-audit` agent alike.
- **Vendored folders in the target addon are read-only, and every spec that can edit code must say so.** Ka0s addons now vendor a shared library at `libs/LibKa0s/` (whole-folder, TOC-listed as its own aggregate `.xml`) and a shared headless test kit at `tests/_kit/` — a *sibling* of the library's ship folder, never under `libs/`. Both are copies. A defect in either is an **upstream** finding: fix it in the library repo, bump the file's LibStub minor, re-vendor the whole folder as its own commit in every consumer. A local patch is reverted silently by the next copy, and the behavior comes back as a regression with **no cause in the consumer's history** — which is why `review` reports these as `[upstream]` and `run-tests` refuses to patch under them even to turn a suite green. **One spec writes into both, and only one way:** `revendor-libka0s` replaces them **wholesale from a tag of the library repo**, never file by file — per-module copying is how cross-major skew gets manufactured — and it is bound by the same `[upstream]` rule everywhere else, including inside its own adoption step. The one deletion it may make inside `libs/` is a file the diff reports as `Only in <Addon>/libs/LibKa0s`, i.e. removed upstream and left behind by `cp -r`, which adds and overwrites but never deletes. The corollary for `new-addon`: the shared subsystems (chat printer, debug console, options toolkit, slash dispatcher, perf harness, test framework) are **consumed, not written** — one setup file per adopted module, holding a **descriptor** plus a **degradation stub**, and nothing else. Don't let any spec drift back toward hand-building or local patching; anything genuinely missing goes upstream as an **additive** field.
- **The `LibKa0s` provenance line lives in the addon's root `CLAUDE.md`, not its `README.md`.** `Bundles [LibKa0s](https://github.com/tusharsaxena/LibKa0s) vX.Y.Z (MIT).` names the tag both vendored payloads (`libs/LibKa0s/` and `tests/_kit/`) were copied from, and it is the **input** to the consumer-side vendored-payload gate the addon runs as `tests/test_vendor_sync.lua` (`testing-§11`). It moved out of `README.md` at **LibKa0s v1.8.1 / test-kit revision 9**, and the gate has **no fallback**: a line left in the README reads to it as no line at all, and a **missing** line fails the case rather than skipping it (unlike an absent sibling checkout, which does skip). Four consequences bind specs here: `new-addon` writes the line into the `CLAUDE.md` stub it scaffolds; `sync-docs` **moves** one it finds in a README rather than refreshing it in place; `bump-version` must **never** roll that `vX.Y.Z` to the addon's new version — it is the library's tag, not the addon's; and `standards-audit` reads it to pick the tag it diffs the vendored copies against, instead of the sibling repo's `HEAD`. The line only moves on a re-vendor, in the **same commit** as the bytes, in both directions.
- **The addon README carries no bundled-library inventory, and its standard badge is not a link** (`documentation-§1`, anti-patterns #58/#59). No `## Libraries` / `## Bundled libraries` / `## Libraries and credits` / `## Credits and libraries` / `## Credits and bundled libraries` section, and no library roll-call smuggled into the intro paragraph — the Ace3/LibSharedMedia/LibDataBroker/LibDBIcon list, the "everything ships inside it, nothing else to install" prose and the `Bundles [LibKa0s] …` sentence all stay out, because a vendored-library list is a contributor fact with two homes that are actually read (`DEPENDENCIES.md`, `docs/ARCHITECTURE.md`) and the README is written for players. What survives is genuinely **external** credit only — a third-party artist, a font, a sound pack — as an optional `## Credits` section placed **last**, after `## Version History`; with nothing external to credit, the section does not exist. The standard badge is the bare `![Standard](https://img.shields.io/badge/Ka0s-WoW_Addon_Standard-yellow)` (`_`, not `%20`) and **MUST NOT** be re-wrapped in `[…](https://github.com/tusharsaxena/WowAddonStandards)` — the binding standards reference is the TOC `## X-Standard:` field and `CLAUDE.md`'s `## Standards compliance (read first)`; the badge declares, it does not navigate. No spec may scaffold, restore or "tidy up" either shape back into an addon.
- **The audit rotation is three kinds of repository, and one repo is deliberately outside it.** The nine addons in `WowAddonStandards/standards/ADDONS.md` are measured against the whole standard; `LibKa0s` against `library-stack-§7`'s applicability list; and `WowAddonStandards` and `wow-addon` against the **documentation lane** — same eight steps, same five artifacts, same `docs/audits/<date>/`, but the four checks are internal consistency between rules, cross-references that resolve, worked examples against the trees they cite, and inventories against the trees they count, graded on how far a defect reproduces rather than on who can reach it (in a repo that ships nothing to a client, the addon grading rule flattens every finding to Low and sorts nothing). Those two entered the rotation late because they are docs-only, and that is exactly what made them expensive: they hold `AUDIT.md` and `agents/review.md`, so a defect in either was reproduced across twenty passes and reviewed by none. **`Ka0sAddonsCommonTasks` is not in the rotation and must not be added** — a README and a tree of frozen planning bundles, no Lua, no TOC, no `libs/`, no suites, nothing a checklist binds to, and an audit there would report the absence of an addon as a stack of MUST failures. The mechanical checks that have no subject in a documentation repo (lint, the headless runner, the vendored `diff -r`, the provenance line, `lizard`) are recorded **not applicable**, never *not run*.
- **`standards-audit` is read-only** on the audited repository — it only writes under `docs/audits/<date>/`. Don't let it edit code.
- **Two cycles, one word.** The *standards* cycle is `revendor-standards` down / `harvest-standards` up, and it carries a **reference**: pointing at the standard, never copying its text into a repo (#49). The *library* cycle is `revendor-libka0s` down, and it carries **bytes**: whole payloads copied from a tag of `LibKa0s` into `libs/LibKa0s/` and `tests/_kit/`. Same verb, different object, opposite rule about copying — don't let a spec generalise from one to the other. Three consequences bind here. The payload is taken from a **tag** via `git archive`, never the working tree, because the consumer's own `tests/test_vendor_sync.lua` resolves the tag its provenance line names and asserts the vendored bytes match the library **at that tag** — an untagged copy passes a local `diff` and then fails the addon's suite, which is how the untagged kit revision was caught upstream. The bytes and the `CLAUDE.md` provenance line move in **one commit**, because that gate fails a split. And `revendor-libka0s` is the **only** spec that moves that `vX.Y.Z`: `bump-version` must never roll it, `sync-docs` migrates a stale line out of a README during a doc sweep, and `revendor-libka0s` removes a README line only when it has just superseded it.
- **The standards cycle runs both ways, and the two halves must not blur.** `revendor-standards` runs **in an addon repo** and carries the standard **down**; `harvest-standards` runs **in the standards repo** and carries the collection's learnings **up**. The load-bearing asymmetry: `harvest-standards` is **read-only on every addon repo and on `LibKa0s`** — not politeness, but what keeps its evidence independent of its argument. If it edited as it swept, the next run would read its own text back as if it were nine repos agreeing. For the same reason neither command ever edits a frozen `docs/audits/` or `docs/reviews/` bundle: those are the harvest's primary source, and their value is that they record what was true against the standard of *their* date. Cross-repo synthesis is `harvest-standards`' whole reason to exist — every other spec here reads exactly one repo — so a run that only re-reads one repo has done nothing new.
- **The ripple is the dangerous part of a standards change, not the rule.** A rule edited in its section and missed in the index blurb, the anti-pattern range, `NEW_ADDON_CONTEXT.md`, `EXECUTIVE_SUMMARY.md` or a playbook leaves the standard **contradicting itself**, and the stale copy is what gets followed. Upstream has already spent a whole patch release cleaning up one incomplete ripple — a count still reading "quartet" beside three named members, which an agent completed from memory with the very file that release had deleted. `harvest-standards` owns that checklist and must discharge it item by item.
- **The quirks catalogue is the one piece of upstream text that *is* vendored into an addon.** Everything else about the standard is pointed at, never copied (#49) — but client quirks are reference data, not instructions, and an addon needs them next to the code that works around them. So they get the `libs/LibKa0s/` discipline instead: a marked block, copied **whole**, replaced **wholesale**, never patched locally, and **stamped with its source version** (a vendored copy without its version cannot be told stale from current — the same reason LibStub minors exist; this is the deliberate exception to "no standard version in a repo file", which governs the *reference*). Below the end marker is the addon's own section: `revendor-standards` must not touch it beyond pruning entries promoted upstream, because it is `harvest-standards`' input and editing it would let one command launder its own text into the other's evidence.
- **Three specs touch the same doc set from different directions; keep the split.** `standards-audit` measures the addon *against* the standard and writes a frozen bundle (read-only, findings). `sync-docs` reconciles docs against the addon's **own code** — count claims, slash parity, dead exports, the comment-citation check, doc scaffolding, and the migrate-then-delete flow for `docs/agent-context.md`. `revendor-standards` reconciles docs against the **current upstream standard text** and edits in place — the three-place reference (`documentation-§6`), retired and unresolvable forms swept out of the **whole repo**, and gate claims the standard has since qualified. The boundary rule: anything needing code analysis is `sync-docs`'s, anything needing the fetched standard is `revendor-standards`'. Two consequences that look like gaps and are not — `revendor-standards` **flags** a missing `docs/` member or root `DEPENDENCIES.md` instead of creating it (an `ARCHITECTURE.md` written without reading the code, or a `DEPENDENCIES.md` written without the evidence, is worse than an absent one) and **reports** `docs/agent-context.md` instead of deleting it (two specs owning one destructive action is how the salvage half gets skipped). It also **must not** rewrite frozen `docs/audits/` or `docs/reviews/` bundles even when they use retired notation: they record what was true against the standard of *their* date, which is what a dated artifact is for. And "revendor" there means the **reference**, never a copy — storing the standard's text in an addon is the same failure as storing the context pack (#49).
- **Two specs may now touch a comment, and their edit boundary is one boundary written twice.** `revendor-standards`' 3b sweep corrects a citation of the **standard** sitting in a code or config comment; `sync-docs`' comment-citation check corrects a comment citing **this repo** — a path that is not there, a `:N` past the end of the file, a `Symbol.Member` with no definition and no call site, a version the tree does not stamp. That last kind is narrower than it sounds and deliberately so: it fires only where the repo holds something authoritative to check against, the migration table's highest `to =` and the `CLAUDE.md` provenance line, so a version quoted in prose with no such authority stays prose. Both are a deliberate, narrow relaxation of "documentation only", and both are fenced on the same four sides: **that sweep/check only**, **comments only** (a string literal, a key or a value is reported, never edited), **explicit confirmation every time** (silence is a decline, not a default), and **never a guessed target** (the user names the replacement or the item stays flagged). The rule's purpose survives intact — an agent licensed to rewrite every repo's `CLAUDE.md` still cannot reach a line that runs. The two are written to match on purpose: **if they ever disagree, that is the bug**, and the fix is to bring them back into alignment rather than to let one drift wider. Widening what either command *reads* never widens what it may *write*, and neither may touch `libs/`, `Libs/` or `tests/_kit/` at all.
- **`finalize` is the only spec that pushes on its own.** Every other git-touching spec here stops at the commit unless it is explicitly told otherwise: `commit.md`'s hard rule is **never push unless the `push` flag was given**, the default being no push, and the flag is consumed only as the leading token so a message containing the word is never acted on. That rule stands; the finalizer overrides it deliberately — it pushes unasked, and says so in its own body — because the ordering it exists to enforce (a vendored library must be **on origin** before a consumer whose docs cite it lands) is not expressible if pushing is somebody else's later step. Don't "fix" the inconsistency by teaching the other specs to push.
- **`finalize` establishes its scope before it acts, and never guesses it.** It covers both the one-repo and the many-repo case, so the scope is a decision, not a given. It proceeds unasked only when the answer is certain — explicit `$ARGUMENTS` (including `here`), exactly one dirty repo, or several linked by *hard* evidence (this session touched each, a vendored folder matches a changed sibling source, a changed file cites a sibling path that also changed). Anything else — unrelated-looking candidates, repos the session never touched, unaccountable dirt — prints per-candidate changes and asks. Too narrow strands half a changeset unpushed while the other half references it on origin; too wide commits someone's work-in-progress under a message that is then wrong for both, which no revert fixes. Don't let it collapse back into "multi-repo only" or into silently picking the likely scope.
- **Commit style:** terse capitalized imperative subjects, no Conventional-Commits prefix; releases commit **directly to `master`**; commits carry a `Co-Authored-By: Claude …` trailer (match the recent `git log`).
