# wow-addon

Claude Code plugin for World of Warcraft addon development.

A focused toolkit for working on WoW addons: scaffolding new addons that are born compliant with the Ka0s WoW Addon Standard, auditing an addon against that standard, refreshing an addon's in-repo reference to it as it evolves, harvesting the collection's learnings back into that standard, bumping an addon's interface version to match Live Servers, syncing documentation against the actual code, releasing new versions, running the addon's test battery, recording the full four-suite battery into frozen dated bundles, recording and interpreting an in-game perf run into frozen `docs/perf-analysis/<run>/` bundles, finalizing a changeset across one repo or several, triaging everything still pending across its code, docs, issues and prior audit plans, managing its GitHub issues, and reviewing changes for WoW-specific correctness (taint, deprecated APIs, frame leaks, missing localization, AceConfig misuse, dead code).

`/wow-addon:new-addon`, `/wow-addon:standards-audit`, `/wow-addon:revendor-standards`, `/wow-addon:automated-tests` and `/wow-addon:perf-analysis` consume the living **Ka0s WoW Addon Standard** at [tusharsaxena/WowAddonStandards](https://github.com/tusharsaxena/WowAddonStandards): they fetch that repo's `NEW_ADDON.md` / `AUDIT.md` / `AUTOMATED_TESTS.md` / `PERF_ANALYSIS.md` playbooks and `standards/` docs at runtime and follow them, so they always track the current standard. All five need network access to that public repo when they run. `/wow-addon:harvest-standards` runs the other way — inside the standards repo, reading the whole collection and promoting what it has learned **into** the standard.

`/wow-addon:revendor-libka0s` is the same cycle for the shared **library** rather than the standard, and it works from local disk instead of the network: it reads the sibling [`LibKa0s`](https://github.com/tusharsaxena/LibKa0s) checkout beside the addon and takes its payload from that repo's newest **tag**. The tag is not a detail — every consumer's `tests/test_vendor_sync.lua` resolves the tag named in its `CLAUDE.md` provenance line and asserts the vendored bytes match the library at it, so a copy taken from an untagged working tree passes a local `diff` and then fails the addon's own suite. That command needs the checkout present, not network access, and it needs `gh` only to file the declines it records.

## Components

### Commands

| Command | What it does |
|---|---|
| `/wow-addon:new-addon <Name>` | Scaffold a new addon born compliant with the Ka0s WoW Addon Standard. Fetches the `NEW_ADDON.md` playbook + context pack and follows them: Ace3 skeleton, the modular layout, MIT, the root doc set (full `README.md`, the `CLAUDE.md` stub, and `DEPENDENCIES.md` — the evidence-based toolchain contract), the canonical `docs/` trio (`ARCHITECTURE.md`, `testing.md`, `smoke-tests.md`), the five verification-and-record docs (`test-cases.md`, `performance.md`, `perf-analysis/README.md`, `automated-tests/README.md`, `automated-tests/RESULTS.md`), the six unconditional **Tier 1** topic-detail docs (`scope.md`, `module-map.md`, `schema.md`, `settings-panel.md`, `data-flow.md`, `common-tasks.md`) with every **Tier 2** trigger evaluated and answered in `ARCHITECTURE.md`'s `## Documentation map`, and the first automated-test bundle before the `v0.1.0` tag — with `automated-tests/README.md` and `docs/testing.md`'s gate table written to state **both** checkpoints from the fetched `automated-tests-§3` (lint + tests gate the commit; the tag is gated on all four suites plus zero functions above CCN 15), and the vendored runner's exec bit set in the **git index** (`git update-index --chmod=+x`), since `core.fileMode=false` on a DrvFs mount makes a bare `chmod` invisible to git — the context pack itself is read at runtime and **never** written into the addon (`documentation-§3`). The README it writes carries the **unlinked** standard badge and **no bundled-library inventory** (`documentation-§1`); the `LibKa0s` provenance line — `Bundles [LibKa0s](…) vX.Y.Z (MIT).`, naming the tag both payloads were vendored from — goes into the root `CLAUDE.md` stub, where the vendored-payload gate reads it. The shared subsystems — chat printer, debug console, options toolkit, slash dispatcher, perf harness, test harness — are **consumed** from the vendored `LibKa0s` library and its test kit, one setup file per adopted module, rather than hand-built. |
| `/wow-addon:bump-interface [number]` | Update `## Interface:` in the current addon's TOC(s) to the current Retail (Live Servers) value. This repo only, not recursive. Pass the number, or omit it to use the current Live value (asks to confirm if unsure). |
| `/wow-addon:sync-docs` | Deep-analyze the addon and rewrite `README.md` / `CLAUDE*.md` / `DEPENDENCIES.md` / `ARCHITECTURE*.md` to eliminate drift. Includes count verification, COMMANDS↔README slash parity, dead-export detection, toolchain-vs-`DEPENDENCIES.md` drift (every entry evidence-backed, never speculative), a **comment-citation check** over the addon's own source and config — a comment naming a path that is not there, a `:N` past the end of the file, a `Symbol.Member` with no definition and no call site, or a version the tree does not stamp — a migration step past the migration table's highest `to =`, a vendored-library tag the `CLAUDE.md` provenance line does not carry — reported with `file:line` and corrected **only on confirmation, comment-only, never to a guessed target** (`libs/`, `Libs/` and `tests/_kit/` excluded as vendored payload) — and ARCHITECTURE.md / DEPENDENCIES.md scaffolding. Enforces the two README shape rules `documentation-§1` states as MUST NOTs: **no bundled-library inventory** (any `## Libraries` / `## Bundled libraries` / `## Libraries and credits` / `## Credits and libraries` heading, or the same roll-call smuggled into the intro prose, comes out — keeping only genuinely external credit, as a `## Credits` section placed last), and the standard badge left as the bare unlinked image. The `LibKa0s` provenance line — `Bundles [LibKa0s](…) vX.Y.Z (MIT).` — is **moved** to the root `CLAUDE.md` if it is still in the README, since that is where the vendored-payload gate reads it (LibKa0s v1.8.1 / test-kit revision 9, no fallback). Leaves the generated docs (`test-cases.md`, `automated-tests/RESULTS.md`) alone — it reports their staleness rather than editing their numbers, and reports a surviving `docs/complexity.md` (retired in standard v2.19.0) rather than syncing it. |
| `/wow-addon:revendor-standards [repos]` | Refresh the addon's **in-repo reference** to the Ka0s WoW Addon Standard so its documentation matches the standard as it exists today — the three-place reference (`documentation-§6`: TOC `## X-Standard:`, the README standard badge — the **bare** `![Standard](…)` image, which `documentation-§1` makes a declaration and **not** a link, so a badge found wrapped in one is unwrapped rather than left or restored — and `CLAUDE.md → ## Standards compliance (read first)`), plus retired and unresolvable forms swept out of the **whole repo**, not just `docs/`: the global `§N.M` notation → `filename-§N`, section filenames renamed upstream, a `filename-§N` whose number is past that section's real range, a root- or `docs/`-set count stated without naming its members, and the retired "drop-in" label for the scaffolding pack — plus a sweep for **gate claims the standard has since qualified** (a "perf and complexity never fail a run" sentence that names no checkpoint, in `docs/testing.md`, `docs/automated-tests/README.md` or the root `CLAUDE.md`), rewritten from `automated-tests-§3` so every gate statement names commit *and* release. `libs/`, `tests/_kit/` and the frozen `docs/audits/`, `docs/reviews/` and `docs/automated-tests/` bundles are excluded from the sweep, and the `RESULTS.md` lead-in is reported as runner-generated rather than edited. Fetches `standards/STANDARDS.md` and every section file its Sections list links (never a hard-coded filename), hard-stops if it can't, and prints a drift inventory before writing. Mechanical items apply automatically; anything overwriting the repo's own prose asks first, as does every item in a multi-repo run. Defaults to the repo at cwd and never widens on its own — pass repos or `all` to sweep siblings. Also vendors the standard's **quirks catalogue** into the addon's `docs/` quirks file as a marked block — copied whole, replaced wholesale, never patched locally and stamped with its source version, under the same discipline as `libs/LibKa0s/` — while leaving the addon's own quirks section alone (that section is `/wow-addon:harvest-standards`' input), and pruning entries from it that have since been promoted upstream. Documentation only, with one narrow exception: a standards citation sitting in a **code or config comment** is reported with `file:line` and corrected only on the user's explicit confirmation, **comment-only** — the same edit boundary `/wow-addon:sync-docs` carries for repo-internal citations, and deliberately identical to it. Otherwise it never edits code, never writes the standard's **rules** into the repo, never creates missing `docs/` members or a missing root `DEPENDENCIES.md`, never hand-edits the generated `test-cases.md` / `automated-tests/RESULTS.md`, never edits frozen `docs/audits/` or `docs/reviews/` bundles, and reports `docs/agent-context.md` rather than deleting it (`/wow-addon:sync-docs` owns that migration). Distinct from `standards-audit`, which measures and writes a frozen bundle, and from `sync-docs`, which reconciles docs against code. |
| `/wow-addon:revendor-libka0s [repos] [--tag vX.Y.Z]` | Carry the current **LibKa0s** into the addon and decide what to do with what arrived — the consumer-side counterpart to the library's release-side re-vendor checklist, and the **only** command that moves the `Bundles [LibKa0s] vX.Y.Z (MIT)` provenance line in `CLAUDE.md` (`/wow-addon:bump-version` must never roll it — it is the library's tag, not the addon's). Reads the sibling `../LibKa0s` checkout and takes the payload from its newest **tag** via `git archive`, never from the working tree, because the consumer's own `tests/test_vendor_sync.lua` resolves the tag the provenance line names and asserts both payloads match the library at it. Reports the delta first — claimed version vs the actual LibStub minors, the per-file minor table read from the tag's `LibKa0s.xml` rather than a hard-coded list, both diffs (content **and** bytes, with content-clean/bytes-dirty read as a line-ending divergence to renormalise, **never** an edit to `libs/`), the kit-revision pairing rule (v1.9.0+ requires kit revision 11 in the same commit), which majors the addon actually consumes, and the **contract delta**: the one class of change no number and no byte can show, where a surface keeps its name and its arguments and moves *when* it is called or what it requires back from a member the host supplied. Read by diffing the tag's `docs/api/<Major>/version-<minors>-docs.md` against the document for the version the addon is on — chaining the documents by each header's `Superseded by` row rather than guessing filenames, and reading that diff for what is **not** `Since`-marked — then binding the result to the addon's own `__Attach*` sites. Those are **adoption blockers, never candidates**: the interview never offers one, and it is fixed in the copy commit or the run stops before the copy, because a payload carrying one passes `luacheck`, the harness and `test_vendor_sync.lua` and is wrong only on screen. Then copies **both payloads whole** — `libs/LibKa0s/` and `tests/_kit/`, never one module, since per-module copying is how cross-major skew is manufactured — rolls the provenance line, gates on `luacheck` + the headless harness, and commits the bytes and the line **together** (the consumer's gate fails a split). Then works out which new surfaces are **candidates**: what arrived for free needs no decision, what needs a host change or a whole unadopted module does — each with `file:line` evidence out of the library's own `docs/api/<Major>/version-*-docs.md` `Since` markers and `CHANGELOG.md` blocks, never from memory, and carrying the addon's own recorded reason for a past decline so a structural refusal is not re-litigated every release. Interviews you **one candidate at a time, most-valuable-first**, saying up front that a decline is filed as a **public** GitHub issue (`state:triaged` or `state:will-not-do`, plus a severity); an early stop leaves the rest undecided and untouched. Implements what you accept — characterization test first, the assertion proving *the same bytes render* rather than *it still runs*, `luacheck` + harness green, **one commit per candidate**. `libs/`, `Libs/` and `tests/_kit/` stay read-only apart from the wholesale copy: a defect in either payload is an `[upstream]` finding, never a local patch. Writes a frozen bundle to `docs/revendor/<date>/` (01_DELTA, 02_CANDIDATES, 03_DECISIONS, 04_EXECUTION_PLAN, 05_SUMMARY). Defaults to the repo at cwd; pass repo names or `all` to sweep every sibling holding a `libs/LibKa0s/`, processed sequentially. **Never pushes.** |
| `/wow-addon:harvest-standards [scope]` | The upstream half of the cycle: harvest what the **whole collection** has learned and promote it into the Ka0s WoW Addon Standard. Run inside the `WowAddonStandards` repo; **read-only on every addon repo**. Sweeps ten categories — convergent patterns (≥3 repos, standard silent → codify) and divergent ones (N solutions → a rule, or a `LibKa0s` extraction candidate), anti-patterns, Midnight quirks, the `docs/audits/` + `docs/reviews/` corpus, standard-internal contradictions an audit had to punt to the user, closed `state:will-not-do` issues across the collection (accepted deviations the standard never heard about, read with `gh issue list --label "state:will-not-do"` — never GraphQL), rules nobody satisfies (and rules nobody cites), `LibKa0s`↔standard drift, undocumented emergent conventions, and tooling gaps whose fix is a lint rule rather than prose. Filters findings three ways before proposing: against the standard version each bundle was measured under (so settled history isn't re-proposed), against `open-evolutions.md` (a known item is a **vote**, not a duplicate), and against an evidence bar of ≥2 repos or 1 repo plus a stated cost. Writes a frozen `harvests/<YYYY-MM-DD>/` bundle, interviews you per proposal (accept / defer / reject), then applies the accepted ones with the **full ripple** — section file, Sections blurb, anti-pattern range, changelog entry, version bump classified as patch/minor/major, `NEW_ADDON_CONTEXT.md` + pack version, `EXECUTIVE_SUMMARY.md`, the `AUDIT.md`/`NEW_ADDON.md` playbooks — and closes by naming the rollout debt per repo. Never auto-resolves an ambiguous signal; never commits or pushes. |
| `/wow-addon:bump-version [X.Y.Z]` | Bump the addon's version everywhere it appears (TOC, code, README badges, Version History table, `CLAUDE*.md`) and roll the release history for everything since the last git tag into its proper home. **`CHANGELOG.md` is a library file, not an addon file** (`documentation-§1`): in an addon repo the history's one mandated home is the README's "Version History" table, an existing root (or `docs/`) `CHANGELOG.md` is left byte-for-byte alone and reported as a violation to fold forward and delete, and one is never created; in a Ka0s-owned library repo — no root `.toc` — the root `CHANGELOG.md` is required and gets the full entry. **Gates the release:** runs the full four-suite battery through the vendored runner **before any file is edited**, and refuses to bump anything unless that run's `manifest.json` shows lint, tests, perf and complexity all passing with zero functions above CCN 15. A suite that was **skipped** is not a pass — absent `lizard`, or no Lua 5.1 interpreter, is reported as **NOT EVALUATED**, names the install command, and stops the release exactly as a failure does; the one exception is `perf` skipped because the addon ships no `tests/perf.lua`, which passes and must be stated as such **in the release notes**, not only in the chat report that scrolls away. Only on a passing gate does it edit anything, write that bundle's `ANALYSIS.md`, and refresh the `RESULTS.md` watch-list disposition for anything that newly crossed a threshold. Proposes a bump if no version is given. |
| `/wow-addon:automated-tests` | Run and **record** the full four-suite battery through the vendored runner — lint, headless tests, offline perf scenarios, `lizard` complexity — writing a frozen bundle to `docs/automated-tests/<YYYYMMDD-HHMMSS>/`, rolling the run into `RESULTS.md` and writing the `ANALYSIS.md`. `lint` and `tests` gate; `perf` and `complexity` are recorded and never fail a run. Fetches the living `AUTOMATED_TESTS.md` playbook. |
| `/wow-addon:perf-analysis [paste]` | Record and **interpret** an **in-game** perf run — the counterpart to `/wow-addon:automated-tests`, and the one recording command that cannot run anything it records. The measurement happened in a live client, in combat, on the player's machine, so **the report and the JSON dump are mandatory inputs that come from the player**: after the run they paste the output of `/<slash> perf report` and `/<slash> perf dump` (one copied debug-log buffer is fine — the command splits it), and if the paste is not there the command **asks for it and stops**. It never invents, completes or reconstructs a capture, and never fills a gap from the offline perf scenarios — those answer a different question and belong to the automated-test bundle that produced them (`automated-tests-§7`). Given the paste it splits report from dump, keeps the lifecycle lines as the capture's provenance, validates the record against the repo (`addon`, `version` vs the TOC, `schema` vs the vendored lib, the report's figures reconciling against the dump's `%.4f`, both arms with `frames > 0`) and **reports** a mismatch rather than correcting it, then derives the bundle stamp from the record's own `timestamp` in **local time** — when the capture happened, not when it was written up. Writes a frozen `docs/perf-analysis/<YYYYMMDD-HHMMSS>/` holding exactly three files: `report.md` (the printed report plus the run's lifecycle log lines), `dump.json` (the record **verbatim**, one line, never pretty-printed or re-ordered) and `ANALYSIS.md` (the write-up), then rewrites the store's standing `README.md` and its index table of captures. The write-up rules that matter: never fabricate a figure, read the **buckets** rather than `deltaMsPerFrame` (below roughly 0.5 ms/frame the delta is **unresolved**, which is not the same fact as zero), treat a negative delta as evidence the environment moved between arms, and say what the arms did not hold constant. An addon with no `core/PerfSetup.lua` has not wired the harness and one holding a recorded `performance-§12` no-combat-path exemption ships no store at all — both are stated, not scaffolded around. Fetches the living `PERF_ANALYSIS.md` playbook. |
| `/wow-addon:diff` | Summarize all uncommitted git changes in the addon — what changed, likely intent, risks. |
| `/wow-addon:commit [push] [ask\|<message>]` | Stage and commit changes with a generated commit message that matches the project's style. Pass `ask` to approve the message first, or a message to use verbatim. **Pass `push` to push the branch afterwards — the default is not to push.** The flag is only consumed as the leading token, so a message containing the word "push" is never mangled or acted on. Never force-pushes, never pushes a commit that did not land, and reports a rejected push rather than pulling or rebasing to resolve it. |
| `/wow-addon:finalize [repos]` | Finish a changeset — in the current repo alone, or across several sibling repos. Establishes the scope first and **never guesses**: explicit repos (or `here`) if you pass them, the single dirty repo if there is only one, all of them when hard evidence proves one changeset — otherwise it prints each candidate's changes and asks. With more than one repo in scope it derives the dependency chain from evidence — a vendored shared library is finalized and **pushed** before the consumers that carry it, and a doc line citing `../<Repo>/…` is an edge like any other — then, per repo: `sync-docs` (content only in a parallel multi-repo run, since nobody is there to confirm per repo; it asks as usual in a single-repo run), that repo's own gate including the vendor-drift diff, `commit`, merge any feature branch with `--no-ff`, push, and delete the branch with `-d`. Independent repos run in parallel, one agent per repo. A red gate, a merge conflict or a rejected push stops that repo alone and is reported with its real output. The one command that pushes unasked — `/wow-addon:commit` pushes only when handed the `push` flag. |
| `/wow-addon:execution-status [plan-path] [brief]` | **Where the planned work stands, in one screen.** Reports what is done, what is running, what is left in order, a percent complete as "n of m" (coded-but-in-review counted separately) and a time to finish with a clock time and the arithmetic behind it. It works for a single multi-step task, where the plan comes from the conversation, and for long runs driven by subagents and dynamic workflows across several repos. The denominator is **everything the conversation planned**: a documented plan's status ledger or checkboxes (`docs/superpowers/plans/`, `_dev/PLAN*.md`, a `TODO.md`, or a path you pass), plus every request and promised step added after it. Each unit's status is reconciled against **evidence**: commits per repo, the working tree, and live background work read with non-blocking `TaskOutput`. Git wins when the ledger lags, and "done" needs a commit or an artifact. The time to finish comes from this effort's own measured pace, per track, with parallel tracks overlapped and the fixed tail added. With nothing measured yet it says so rather than guessing. `brief` shortens the report to the headline, the phase table and the next three steps. **Read-only:** it never ticks a ledger, commits, restarts work, waits on a running task or messages a running agent (a message can wake a duplicate of a workflow's subagent). |
| `/wow-addon:run-tests` | Run the addon's entire test battery — auto-detects and runs luacheck lint, the headless Lua `tests/` harness, and any Makefile `test` target, then reports a combined pass/fail summary. Offers to diagnose and fix failures. Deliberately skips non-gating measurement runners such as `tests/perf.lua`: they measure rather than verify, and their scenarios are not test cases. The `lizard` complexity report is out of scope for the same reason and a stronger one — its checkpoint is release, and gating commits on it is what teaches a collection to reach for `--no-verify`. Treats the vendored `tests/_kit/` harness as harness, not a suite, and surfaces a kit-sync (vendor-drift) failure distinctly, since its fix is a re-vendor rather than an edit. |
| `/wow-addon:issue-audit [here\|all\|<repo>] [scope]` | **Discovery half of the issue pair.** Sweeps the addon for everything still hanging — TODO/FIXME/stub markers, unexecuted items from the newest audit and review execution plans, doc open questions and Known Limitations, an `Unreleased` CHANGELOG section, stashes and follow-up commits, and recorded-but-unacted Claude memory — reconciles each against the issue store by **evidence hash**, and files anything genuinely new as an open issue labelled **`state:untriaged`** plus a **`severity:`** label, after showing you the list. **It never interviews you and never changes code**, which is what makes it cheap enough to run often and across every repo at once. Items already tracked are counted, not re-filed; terminal ones are dropped. Creates the eight collection labels (`state:*`, `severity:*`) if the repo lacks them, and repairs any issue that arrived without a status or severity label — stripping a leftover legacy `[status]` title prefix on the way. Defaults to the repo at the cwd; pass `all` or a repo name. Narrow further with `code`, `docs`, `issues`, `memory`, or a path. Requires `gh` — the store is remote. |
| `/wow-addon:issue-triage [here\|all\|<repo>]` | **Decision half of the issue pair.** Takes every open `state:untriaged` issue, **most severe first by its `severity:` label**, and puts each to you one at a time with its verbatim evidence and location — 2–3 concrete resolutions specific to that item, plus **Keep it open — real work, not now** and a permanent **Will not do**. Records the call by swapping the `state:` label in a single `gh issue edit` and appending a rationale comment; `state:will-not-do` and `state:done` are closed, `state:triaged` stays open. A severity you dispute is re-labelled on the spot and the queue re-orders. **Decision-only: it changes the issue store and nothing else** — accepting that something should be done records the approach on a `state:triaged` issue rather than writing the code. Stopping early leaves the rest `state:untriaged` and untouched, so silence is never recorded as a decision. Defaults to the repo at the cwd. |
| `/wow-addon:issue-fetch-all [filter]` | List the GitHub issues on the addon's repo (via `gh issue list`). Filter by **status label** (`untriaged`, `triaged`, `done`, `will-not-do`), by **severity** (`critical`, `high`, `medium`, `low`), by any other label, or pass `closed`/`all`; status and severity filters combine, since both are plain `--label` queries. The report is sorted most-severe-first and carries status, severity, state, labels, author and age, with the URLs below it and status/severity tallies above. **Read-only** — a missing label is reported, never repaired here. |
| `/wow-addon:issue-add` | Create a well-formed GitHub issue (via `gh issue create`). Gathers a title, tag (bug/enhancement), **severity** — proposed with a justification you can overrule — and details; fuzzy input is fine. Formulates a clean issue with a plain title (no status prefix) carrying `state:untriaged` (or `state:triaged` when you are explicitly filing something already postponed), the `severity:` label and the tag, shows it for approval, then creates it. Ensures the eight collection labels exist first. |
| `/wow-addon:issue-summary [all\|here\|<repo>]` | **How much, how bad, and where — counts only.** Prints three cuts: a **status × repo grid** (`done` / `will-not-do` / `triaged` / `untriaged`), a **severity × repo grid over open issues only** (closed severities say nothing about what to do next), and a **status × severity crosstab** whose `untriaged × critical` cell is the first thing worth reading. Then a short read of what the numbers imply — concentration, whether volume and severity point at different repos, how much of the backlog is unsized — grounded in the grids and nothing else. **Defaults to the whole collection**; pass `here` or a repo name. Never lists issues. Read-only apart from adding a missing `state:` label, always announced; it never assigns a severity, since that needs the body read. |
| `/wow-addon:issue-details [here\|all\|<repo>] [states] [severities]` | **What, item by item.** Groups issues by status into sub-sections and lists each with its **severity**, title, a one-line description drawn from the body, age and URL, **most severe first** within each block. A per-repo severity tally sits under the repo heading. Defaults to the live store — `state:untriaged` and `state:triaged` — because the terminal states are history and printing them by default buries the ones that need you; pass `done`, `will-not-do`, `closed` or `all` to widen it, or a severity to narrow it. Status is a heading rather than a column because the row-width budget is a correctness constraint and severity earns the space more. Never invents a description: an issue whose body has nothing usable gets `—`. Read-only apart from the same announced status-label repair. |

### Subagents

| Agent | When to invoke |
|---|---|
| `review` | Focused review of WoW-specific issues: taint and combat lockdown (incl. secret-value leakage), event over-registration, frame leaks, deprecated APIs, missing localization, AceConfig/Settings UI misuse, NBSP/tooltip-pattern bugs, dead exports, and project-internal convention drift (COMMANDS dispatcher parity, single-write-path bypass — applied only when the addon has those conventions). **Measures before it reviews:** re-runs every suite that works outside the game client — `luacheck`, the headless `tests/` harness plus a fresh `--list` inventory, the offline `tests/perf.lua` scenarios, `lizard` to a scratch path, a `Makefile` `test` target, a vendored-copy `diff`, and — when the sibling repos are on local disk — a **cross-addon pass** over the four collisions only a same-session load of the whole collection exposes (slash tokens, vendored LibKa0s minors, vendored payload bytes, `## Interface:`), each census scoped to the TOC-derived load list and diffed against a recorded clean baseline rather than re-derived — and grounds findings in today's numbers rather than the committed `docs/test-cases.md` / `docs/automated-tests/RESULTS.md` / `docs/performance.md`, reporting where those artifacts have gone stale. Fresh output goes to scratch: it never regenerates a committed report (that's release work) and never edits a test to change a result. A missing tool is a stated skip, never an inferred pass. Anything needing a login is not run — it becomes the in-client checklist in `03_SMOKE_TESTS.md`. That measurement also opens new ground: unfalsifiable test cases (`testing-§12`), hand-maintained load lists where the TOC derivation is required, perf buckets no bracket reaches, and lint config that hides a real problem. **Grades by reachability, not defect kind alone:** every finding carries a `Reachability:` line — who hits this, in what configuration, today — written *before* its severity is chosen, and the buckets bind to it (Critical needs both a qualifying defect kind and a normal install that reaches it; a developer-only verb, a comment, or a test-inventory-only defect cannot be High whatever its kind). A degraded or fallback path is explicitly **not** capped — cap on who reaches it, never on which branch it sits in. Before the bundle ships it re-reads every `file:line` it cites, quotes the cited text beside it, reconciles figures across all five artifacts, and drops or corrects anything that does not resolve; every count names the exact command **and its scope**. Vets its own findings and proposed changes against the living Ka0s WoW Addon Standard so remediation never introduces a new deviation — a guardrail, not a full audit (that's `standards-audit`); if the standard can't be fetched it proceeds anyway and notes the skip. Treats vendored code (`libs/`, `tests/_kit/`) as read-only: a defect there is reported as an `[upstream]` finding to fix in the library repo and re-vendor, never a local patch. For subsystems the addon consumes from a shared library, it reviews the **descriptor** and the **degradation stub** — not the library's implementation — and never proposes re-hand-rolling what the library provides. Invoked via `/wow-addon:review`. |
| `standards-audit` | Read-only compliance audit against the Ka0s WoW Addon Standard. Fetches the living `AUDIT.md` playbook + `standards/STANDARDS.md` (the standard's index) at runtime, follows the index's Sections list to fetch every section file, measures the repository section-by-section and against the `anti-patterns` list, and writes a frozen `docs/audits/<YYYY-MM-DD>/` bundle (current state, deviations with stable IDs, evidence, remediation design, execution plan). **Settles which rule set binds the repository before anything else**, because the rotation is three kinds and not one: the nine addons take the whole standard, `LibKa0s` takes `library-stack-§7`'s applicability list, and the two documentation-and-tooling repos — `WowAddonStandards` and `wow-addon` — take the **documentation lane**, same steps and same artifacts but measuring internal consistency between rules, cross-references that resolve, worked examples against the trees they cite, and inventories against the trees they count, graded on how far a defect reproduces rather than on who can reach it. Those two hold `AUDIT.md` and `agents/review.md`, the documents every other pass runs on, so a defect in either was reproduced across twenty passes and reviewed by none until they entered the rotation; `Ka0sAddonsCommonTasks` is deliberately outside it, being frozen planning bundles with nothing for a checklist to bind to. **Grades each deviation by impact, not rule strength** — High is reserved for what a user, their SavedVariables or their session can hit today, so a doc-only MUST failure is Low or Info and still names its MUST — and files **one root with `derived from <ID>` dependents** where several observations follow from a single unadopted subsystem, reporting both the roots-only headline tally and the total. **Reads the recorded-deviation register before filing any MUST as open** (`docs/ARCHITECTURE.md` § Documented deviations, the repo's issue-audit **GitHub issue store** read via `gh issue list` and keyed on the `state:` label, root `CLAUDE.md`, `docs/scope.md`): a ratified row makes the gap a recorded deviation outside the MUST tally, and a decline recorded *only* as a closed `state:will-not-do` issue with no register row is itself a `documentation-§3` deviation to file. Re-reads and quotes every `file:line` it cites before writing, reconciles figures across artifacts, and states each count's exact command **and scope**. Runs the mechanical checks rather than reasoning about them — lint, the headless suite, a `diff -r` of every vendored Ka0s-owned library against its sibling source repo **at the tag the addon's root `CLAUDE.md` provenance line names** (not the sibling's `HEAD`, which measures scheduling rather than compliance; that drift is invisible to both repos' test suites), with the line's own placement audited too — it lives in `CLAUDE.md` and not `README.md` since LibKa0s v1.8.1 / test-kit revision 9, and a missing line is a failing gate rather than a skip — and the `lizard` complexity run compared against the addon's latest automated-test bundle (`docs/automated-tests/<run>/complexity.txt`) and the `RESULTS.md` watch list, recording the drift and how stale that run's stamp dates it. An absent tool or sibling repo makes a check **not run**, reported as such, never inferred. Never modifies addon code. Invoked via `/wow-addon:standards-audit`. |

### Hooks

- **Line-ending normalization on Write/Edit/MultiEdit** — when a file is written/edited inside a git repo, the plugin asks git what that file's `.gitattributes` declares and normalizes to it: **CRLF** in a client-bound Ka0s repo (the addons and `LibKa0s`), **LF** in one that ships nothing to the WoW client (the standards repo and this one). Every Ka0s repo declares one or the other (`line-endings`). It asks for `text` as well as `eol`, so a file marked `binary` is left alone even though the pin still answers `eol: crlf` for it (`line-endings-§7`); silent likewise on files with no declared `eol`, and it never blocks a write. Lives at `hooks/hooks.json` + `scripts/normalize-eol.sh`.
- **Bounded heavy runs on Bash** — a `PreToolUse` hook refuses an unbounded `lua tests/run.lua` / `lua tests/perf.lua`, `run-automated-tests.sh`, `luacheck` or `lizard` and names the bounded runner to prefix instead: `~/.claude/wow-addon/bin/ka0s-bounded <command>` (a symlink the hook keeps pointed at the installed `scripts/ka0s-bounded`). The runner caps process memory (`ulimit -v`, `KA0S_KIT_PROC_MB`, default 2048), the process tree's memory and task count (a `systemd-run --user --scope`, `KA0S_KIT_TREE_MB` default half of RAM, `KA0S_KIT_TASKS` 256) and wall-clock time (`KA0S_KIT_TIMEOUT_S`, 900), and queues on a machine-wide `flock` slot pool (`~/.cache/ka0s-kit/slots`, `max(1, MemAvailable×0.6 / KA0S_KIT_SLOT_MB)` slots, or `KA0S_KIT_SLOTS`), so several repos' suites can run in parallel without exhausting memory. Exit codes pass through; 124 (timeout) and 137 (killed) get a one-line explanation. Lua runs in a repo whose `tests/_kit` is LibKa0s kit revision 23+ are let through, because that kit bounds itself with the same variables. Why: an unbounded runaway suite once OOM-killed a whole WSL2 VM and the session driving it. Opt-out for one command: an inline `KA0S_BOUNDED_HOOK=off` assignment.

## Install

Install straight from this GitHub repo — no manual cloning required. In any Claude Code session, run these three commands:

```
/plugin marketplace add tusharsaxena/wow-addon
/plugin install wow-addon@wow-addon
/reload-plugins
```

Step by step:

1. **`/plugin marketplace add tusharsaxena/wow-addon`** — registers this repo as a plugin marketplace. Claude Code clones it for you. (You can also pass the full URL `https://github.com/tusharsaxena/wow-addon.git` or, if you already have a local clone, the path to it.)
2. **`/plugin install wow-addon@wow-addon`** — installs the plugin (`wow-addon`) from the marketplace (`wow-addon`). When prompted for scope, choose **user** to enable it in every project on this machine, or **project** to enable it only in the current project.
3. **`/reload-plugins`** — activates the plugin in the current session without a restart.

After install, the commands, the `review` and `standards-audit` subagents, the line-ending hook and the bounded-runs hook are available in every Claude Code session.

## Updating

When the repo changes (new commands, updated agent, new hook), pull the latest and reload:

```
/plugin marketplace update wow-addon
/reload-plugins
```
